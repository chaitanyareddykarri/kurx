# Security overview

See [`secret-management.md`](secret-management.md) for the secrets policy specifically. This doc covers the rest.

## Authentication

JWT bearer tokens. Access tokens are short-lived (1h); refresh tokens (30d) are rotated on every use and stored hashed (SHA-256) — reusing an already-rotated refresh token is treated as theft and revokes every active session for that user (D-014). `TokenValidationParameters` explicitly validates issuer, audience, signing key, and lifetime.

**Two signing generations are live at once (D-099).** Validation accepts both: an ES256 token carries a `kid` resolved live from the `signing_keys` table by `IssuerSigningKeyResolver`, and a token with no `kid` falls back to the legacy HS256 shared secret (D-009). `TokenService.CreateAccessTokenAsync` mints ES256 **when an `ISigningKeyService` is available**, otherwise HS256 — so which one a given deployment issues depends on its wiring, and the dev compose stack currently issues `alg: HS256`. Dropping HS256 validation outright would sign every current user out; it is removed once no HS256 token can still be within its lifetime. The public keys are served at `/.well-known/jwks.json`, and the gates that must pass before ES256 *issuance* is enabled are in [`../AUTHENTICATION_HANDOVER.md`](../AUTHENTICATION_HANDOVER.md) §8. Private keys are wrapped at rest — see [`secret-management.md`](secret-management.md) on `SIGNING_KEY_PROTECTION` (D-102a). A successful phone number change (`POST /v1/me/phone/verify`) revokes every other active refresh token the same way and issues a fresh pair to the requesting device (D-038) — a device left on the old number stops being able to refresh immediately, though its current access token remains valid until its own natural ≤1h expiry (inherent to stateless JWTs; only refresh tokens are revocable).

Claims are parsed defensively: `Guid.TryParse` (not `Guid.Parse(...)!`) on the `sub` claim in every endpoint that needs the caller's user id, so a malformed or missing claim returns a clean `401 invalid_token` instead of an unhandled-exception `500`.

## Authorization

Authority is **never carried in the JWT** and never trusted from a token claim — every check reads live state per request, so a grant, revoke, or suspension takes effect on the next request. See [`.claude/memory/trust-verification.md`](../../.claude/memory/trust-verification.md) for the full model.

- **Platform roles (M2, D-040)** — `SuperAdmin` / `VerificationReviewer` / `FinanceOps` / `Support` / `ReadOnlyAuditor` live in `platform_roles`. `PlatformRoleClaimsTransformation` runs on every authenticated request: it **strips any token-supplied `platform_role`/`kurx_admin` claim** (anti-forgery) and re-adds the user's current roles from the DB. ASP.NET policies (`KurxAdmin` → SuperAdmin, `VerificationReviewer`, `FinanceOps`, `Support`) gate the admin / verification / fraud endpoints, which now exist (M5/M12/M13). The old `users.IsKurxAdmin` boolean was **removed** in M1 (D-041); profile fields (headline/bio/education/skills/links) are authority-zero — never read by authorization or verification.
- **Per-org resource roles (D-015)** — Owner/Manager/Staff/Finance, resource-specific, checked fresh against the database on every request (`OrgService.RoleAsync`; `IEventAuthority.ResolveOrgAsync` for org-owned assets).
- **Event authorization is a single service (D-269/D-272)** — `IEventAuthority` resolves a caller to one ordered level (`None < Participant < Staff < Manager < Admin`); every permission is a threshold on it, in one table. The event's **creator** reaches `Manager` with no membership (D-268), as does a `Representative` (D-075) or an `Owner`/`Manager` seat; `Participant` is reached by an accepted programme participation **or a live ticket** (D-272); `Finance` holds nothing on events. This replaced eleven per-service copies whose drift had hidden two live permission defects — see D-269. **It performs no capability resolution**, and the Capability Engine performs no authorization; the two never consult each other.
- **It governs the audience too, not only management (D-272).** Two permission families sit on the one ladder: management (`ViewAttendees`, `ViewAnalytics`, `ManageContent`, `ManageLifecycle`, `Delete`) and audience (`Participate` — event feed, post attachment, chat room; `ModerateAudience` — chat `Host`). **An organization membership is never, by itself, event access.** A bare `db.Memberships.Any(m => m.OrgId == ev.RepresentingOrgId && m.UserId == x)` is the bug pattern D-272 removed: it grants `Finance`, and grants the event's own creator *nothing* unless a self-representation row happens to exist — which meant three audience surfaces silently depended on a synthetic membership for owner access.
- **Trust capability gates (M7, D-046)** — paid organizing, payouts, and org representation are gated on live capability flags composed from identity (M3), org verification (M5), membership (M6), and fraud (M13) state; L0–L5 are display labels. The **paid-event money gate is read live at charge time** (`EventService.GetPaymentReadinessAsync`, M8/D-047): Published + a priced ticket type + organizer `CanOrganizePaid` + org `Verified` — a suspension or fraud flag stops payments on the very next request, never a stored flag.
- **The identity proofs inside those gates are switchable outside Production (D-323).** `IDENTITY_VERIFICATION_BYPASS=true` makes `CanCreatePublicEvent`, `CanOrganizePaid` and `CanReceivePayout` stop requiring government ID, PAN and bank ownership. It is dev/test scaffolding for a gap, not a feature: those three proofs are all answered by `MockKycProvider`, so the gate is real logic over simulated evidence and enforcing it outside Production establishes nothing. Three properties keep it from being a hole, and a reviewer should reject any change that breaks one: **fraud is outside it** — `fraudClear` (blacklist + risk, M13) is still ANDed into all three, because it is the one input with a real implementation behind it; **the facts are never forged** — `identity_verified`/`bank_verified` keep reporting what is actually on file, so no profile ever claims a verification nobody performed; and **it fails closed** — `AddKurxInfrastructure` throws at startup if it is set in Production, and every unset or unrecognised value resolves to enforced, so the failure mode is a refusal rather than an open gate. Default off; the test suite runs with it off and keeps proving the real rules. It should be deleted, not merely unset, once a real DigiLocker/penny-drop adapter ships.
- **SignalR hubs** all carry `[Authorize]` except `LoginHub`. `ScanHub`, `SalesHub` and `ChatHub` additionally **re-check membership from the database before the group join succeeds** (D-017), so a connected client can't subscribe to another org's feed or another event's room by guessing an id — `ChatHub.JoinRoom` requires a `ChatMember` row that is not banned, `SalesHub`/`ScanHub` require an org membership. `NotificationHub` has no such check *and needs none*: it joins `user:{userId}` taken from the caller's own validated `sub` claim, so a caller can only ever subscribe to itself. `LoginHub` is anonymous by design (AM9) — a browser with no session yet is the whole point — and authorizes on the **poll token** issued by `/v1/auth/login/password` (`CanWatchAsync`), the same secret that gates `/v1/auth/login/status` (D-080); it carries a status signal only, never tokens.
- **Chat security** — authorization model, the two rate-limiting layers, moderation/reporting, audit logging, attachment validation, and E2EE/MLS readiness are documented in [`docs/EVENT_CHAT_ARCHITECTURE.md`](../EVENT_CHAT_ARCHITECTURE.md) (D-104).

## Error handling

A global `IExceptionHandler` (`GlobalExceptionHandler`) catches anything unhandled and returns an RFC7807 `ProblemDetails` response — never a raw stack trace or ASP.NET Core's default error page. In `Development`, the exception message is included in `detail` for debugging; in any other environment it's a generic message plus the `correlationId` to look up in logs.

## Input validation

Validation lives in **two** places, and knowing which applies to a given endpoint matters when reviewing one.

**Boundary validators.** A request DTO opts in by chaining `.WithValidation<TBody>()`, which runs its `AbstractValidator<TBody>` (`Kurx.Api/Validation/`) in a generic `IEndpointFilter` before the handler executes, returning RFC7807 on failure. Measured on this tree: **43 validators covering 57 of 517 operations**. Shape, range and format rules belong here — length bounds, `EndsAt > StartsAt`, enum parseability, valid absolute URL, valid JSON.

**Service-layer validation.** The remaining ~131 request bodies have no validator and do **not** validate inline in the endpoint lambda either — they pass straight to a service that returns a `ServiceResult` error code, which the endpoint maps to a `ProblemDetails`. `POST /v1/auth/password/change` is the pattern: no `ChangePasswordBodyValidator` exists, and `PasswordService.ChangeAsync` returns `password_not_set` / `account_locked` / `invalid_credentials`. This is deliberate wherever the rule needs database state — a validator cannot know whether a password is reused, a room is muted, or a seat is taken.

> This section previously claimed *"Every request DTO has a FluentValidation validator … there is no manual validation left inline"*. Coverage is 11% of operations, not 100%. The claim mattered because it is exactly what a reviewer would rely on to skip checking a new endpoint's inputs. Corrected 2026-08-08. **Reviewing a new endpoint means confirming its inputs are checked in one of the two places above — never assuming the filter caught it.**

## Logging

Correlation IDs, user IDs, and org IDs are attached to structured logs (Serilog `LogContext` + `EnrichDiagnosticContext`) — see `docs/architecture/overview.md`. Secrets are never logged by application code. **OTP codes are, by the default dev provider** — `ConsoleSmsProvider` (`Kurx.Infrastructure/Providers/SmsProviders.cs`) logs the full message body at `Information`, including the code:

```
[sms→console] to=+919xxxxxxxxx senderId= template= msg=Your Kurx code is 332760. It expires in 5 minutes.
```

This is the stand-in for real delivery (D-008) and it is how a developer completes a login locally, so it is intentional — but `SMS_PROVIDER` **defaults to `console`**, which means the exposure is on unless someone turns it off. Setting `SMS_PROVIDER=sns` is what removes it; `AddProvider` refuses any unimplemented value, so this cannot be half-configured. `ConsoleWhatsAppSender` logs message text the same way. `ConsoleEmailSender` does not — it logs recipient, subject and attachment count only, never the body, so the emailed-OTP path is already clean.

> This section previously named the console **WhatsApp** sender as "the one place an OTP is visible in logs", framed as an edge case pending `WHATSAPP_PROVIDER`. OTPs are delivered over SMS; the emitter is `ConsoleSmsProvider` and it is the default. An operator auditing log exposure would have checked the wrong flag and concluded there was none. Corrected 2026-08-08 against a live capture from the running container.

## Web session handling

The Next.js `web` app stores the access/refresh tokens in httpOnly, `SameSite=Lax` cookies (`secure` in production) set via a server action — never in `localStorage` or client-readable storage. The `(app)` route group calls `requireSession()` before rendering, which validates the session against `/v1/me` and redirects unauthenticated users.
